# 审批引擎标准性与建模评估：问题清单

> 状态：AR-01–AR-09 已修复（2026-11-23）；AR-10（引擎拆分重构）仍作为独立重构项排期。
> 范围：后端 `api/modules/approval` 的引擎、领域模型与接入契约；AR-01 的 Web 入口已同步。
> 结论摘要：按 OA 审批域的轻量引擎标准衡量，模型骨架合理（定义/运行分离、版本化、快照、节点状态持久化、乐观并发、在途唯一约束均具备）；按 BPMN/通用工作流引擎衡量不是标准实现，也不以该标准要求它。主要缺口集中在运维出口、事务边界与发布期校验，见第二节。
> 本文只登记问题与待确认事项，不代表已排期或已批准修改。

## 一、评估口径

- **标准**：以「自研轻量审批引擎」为定位，参照主流审批产品（钉钉、飞书）与 BPMN 子集语义，不要求全量 BPMN 元素。
- **合理**：定义与运行分离、版本不可变、运行快照、并发原子性、模块边界清晰、动作与状态约束集中。
- **问题分级**：
  - `P1`：生产运维或数据一致性缺口，建议优先处理。
  - `P2`：语义不完整或实现与文档/校验不一致，排期处理。
  - `P3`：语义需业务确认或可维护性优化。

## 四、判定为有意简化、不列为问题

以下能力缺失属于当前定位下的有意取舍，不登记为缺陷：

- 不实现全量 BPMN 元素（子流程、事件网关、边界定时器、补偿等）。
- 超时仅提醒，不自动通过/拒绝（第一阶段「明确不做」的延续）。
- 不内置表单引擎，字段元数据由业务描述符声明。
- 不做在途实例迁移到新定义版本。
- 不做动态审批人表达式、代理与第三方系统发起审批。

## 五、符合主流建模、无需调整的部分

- 定义/运行分离与版本化：`Code` 多版本、发布后不可改、基于旧版派生草稿（`ApprovalFlowEntities.cs:9-74`）。
- 运行快照：实例冻结定义编码/名称/版本，任务冻结节点名称（`ApprovalRuntimeEntities.cs:10`）。
- 有向图执行与节点状态持久化：排他/并行网关、汇聚策略、死分支传播与分支剪枝（`ApprovalFlowGraph.cs:188-299`）。
- 并发控制：实例 `Version` 乐观锁、任务条件更新、`(TenantScope, RunningKey)` 唯一索引（`ApprovalEngine.cs:1316-1369`）。
- 模块边界：审批模块只依赖 Contracts，业务模块注册描述符并消费终态集成事件，不反向引用业务实现。
