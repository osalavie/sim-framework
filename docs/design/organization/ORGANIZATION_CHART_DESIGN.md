# Organization Chart 与数据范围权限设计

> 状态：第一阶段（组织单位树、单位编码与成员归属，以及单一读取端口 `IOrganizationDirectory`）已实施；数据范围、权限解释与审计仍为设计提案。
> 目标：在现有“用户—角色—权限”RBAC 之上增加组织层级和数据范围，让管理员能看懂、能预览、能审计，而不是依赖隐含规则猜测最终权限。

## 一、设计结论

Organization Chart 不是单纯的部门树。完整系统由三条互相独立、最终在请求时汇合的控制线组成：

1. **功能权限**回答“可以做什么”，例如查看、创建、编辑、删除、导出。
2. **数据范围**回答“可以对哪些记录做”，例如仅本人、本组织、本组织及下级、指定组织、全部。
3. **字段策略**回答“记录中的哪些字段可见或可改”，例如手机号脱敏、成本字段不可见。

最终授权必须同时满足：

```text
允许访问 = 功能权限通过
        AND 记录位于有效数据范围
        AND 资源自身策略通过
        AND 字段策略允许展示或修改
```

前端只负责解释和预览；后端必须在查询和写入入口执行相同规则。菜单隐藏不能作为安全边界。

## 二、管理端信息架构

入口建议放在“授权管理 → 组织与数据权限”，使用一个工作台承载三个紧密关联的视图，避免管理员在多个页面之间来回比对。

### 2.1 顶部上下文栏

始终展示当前正在检查的上下文：

- 当前组织节点。
- 当前角色或用户。
- 当前业务资源，例如“客户”“订单”。
- “查看最终权限”开关。

“最终权限”表示已经合并用户全部角色、主组织、兼职组织和资源策略后的实际结果；“配置来源”则分别展示每个角色的原始设置。

### 2.2 左侧：组织导航

- 树形列表是主要导航，默认展开到当前节点的同级。
- 节点同时显示名称、编码、成员数和状态，不只依赖图标或颜色。
- 支持搜索后保留祖先路径，搜索结果不能脱离组织上下文。
- 停用节点使用“已停用”文本标签，并禁止新增成员或成为新数据的归属组织。
- 拖拽移动属于高风险操作，必须显示目标路径、影响成员数和受影响数据范围，并二次确认。

### 2.3 中间：Organization Chart

- 默认采用从上到下的层级图，节点卡片显示负责人、成员数、直属子组织数。
- 点击节点只改变选中态和右侧详情，不直接进入编辑。
- 连接线只表达组织父子关系，不混入汇报线、项目组或权限继承线。
- 兼职、虚线汇报等非树关系通过节点详情中的“附加关系”表达，避免图面失真。
- 组织超过 200 个节点时按层级懒加载；超过 1,000 个节点时默认使用树表，Chart 仅渲染局部子树。

### 2.4 右侧：权限解释面板

右侧面板按以下顺序展示，顺序即管理员的决策路径：

1. **当前结论**：允许或拒绝，以及影响的组织数量。
2. **数据范围**：范围类型、起始组织、是否包含下级、指定节点。
3. **功能权限**：查看、创建、编辑、删除、导出等权限清单。
4. **来源解释**：哪一个角色、哪一个成员关系或哪一条资源策略产生了结果。
5. **风险提示**：范围扩大、跨组织、停用组织、无明确归属、字段敏感等。

每一条结论都使用“图标 + 文本 + 标签”，不能只用绿色或红色表达。

### 2.5 移动端

- 将三栏收敛为“组织 / 权限 / 成员”三个页签。
- Organization Chart 改为可逐级进入的树卡片，不要求用户在小屏幕上缩放完整组织图。
- 主要触控区域不小于 44 px。
- 权限配置使用分步抽屉：选择范围类型 → 选择组织 → 预览影响 → 保存。

## 三、领域模型

### 3.1 OrganizationUnit

| 字段 | 说明 | 约束 |
| --- | --- | --- |
| `Id` | 组织单元 ID | `Guid` |
| `TenantId` | 租户 | 必须参与唯一索引和查询隔离 |
| `ParentId` | 父组织 | 根节点为空；禁止形成环 |
| `Code` | 稳定编码 | 同一父节点下唯一（不同父节点可重复），创建后不可修改 |
| `Name` | 展示名称 | 同一父节点下建议唯一 |
| `Path` | 物化路径 | 例如 `/root-id/sales-id/` |
| `Depth` | 层级深度 | 用于限制最大深度和查询 |
| `ManagerUserId` | 负责人 | 可空；不等同于权限管理员 |
| `SortOrder` | 同级排序 | 稳定整数 |
| `Status` | `Active` / `Disabled` | 停用不等于删除 |
| `Version` | 乐观并发版本 | 移动、重命名时校验 |

`Path` 用于高频祖先/后代查询，但 `ParentId` 仍是权威关系。移动节点必须在一个事务中更新本节点及全部后代的 `Path`、`Depth` 和版本。

### 3.2 OrganizationMembership

一个用户可以属于多个组织，但必须显式标记唯一主组织：

| 字段 | 说明 |
| --- | --- |
| `OrganizationUnitId` | 所属组织 |
| `UserId` | 用户 |
| `IsPrimary` | 是否主组织，同一用户只能有一个 |
| `PositionName` | 岗位名称，仅用于展示 |
| `MembershipType` | `Primary` / `Concurrent` / `External` |
| `ValidFrom` / `ValidTo` | 可选有效期 |

组织负责人是一种组织属性，不自动授予“管理本组织数据”权限。负责人仍需通过角色获得功能权限和数据范围，避免把人事关系偷偷变成授权关系。

### 3.3 RoleDataScope

数据范围按“角色 + 资源”配置，而不是只在角色上放一个全局范围。这样“销售主管可看本区域客户，但只能看自己的薪酬”可以被准确表达。

| 字段 | 说明 |
| --- | --- |
| `RoleId` | 角色 |
| `Resource` | 稳定资源编码，例如 `qms.ocap` |
| `ScopeType` | 数据范围类型 |
| `AnchorMode` | 从主组织、全部有效成员组织或固定组织起算 |
| `IncludeDescendants` | 自定义范围中的节点是否包含下级 |
| `ConditionVersion` | 策略版本 |

`Custom` 范围使用关联表保存节点，不将 ID 数组塞进 JSON：

| 字段 | 说明 |
| --- | --- |
| `RoleDataScopeId` | 范围配置 |
| `OrganizationUnitId` | 指定组织 |
| `IncludeDescendants` | 是否包含该节点下级 |

### 3.4 业务数据归属

需要数据范围控制的业务实体至少提供：

- `TenantId`：租户隔离，始终先于数据范围执行。
- `OrganizationUnitId`：记录归属组织。
- `OwnerUserId`：记录所有者，用于“仅本人”。

归属字段应在创建时写入并持久化，不能每次根据用户当前主组织动态推断，否则员工调岗会让历史数据悄悄改变归属。调岗后的历史数据是否迁移必须由业务操作显式完成并审计。

## 四、数据范围类型

| 类型 | 含义 | 典型角色 | 查询语义 |
| --- | --- | --- | --- |
| `None` | 无数据 | 未完成授权的新角色 | 恒为 false |
| `Self` | 仅本人拥有的数据 | 普通员工 | `OwnerUserId == CurrentUserId` |
| `OrganizationOnly` | 起始组织，不含下级 | 财务专员 | `OrganizationUnitId IN anchors` |
| `OrganizationAndDescendants` | 起始组织及全部下级 | 区域负责人 | `Path` 命中任一起始路径 |
| `Custom` | 指定多个组织，每个节点可选是否含下级 | 跨区域项目负责人 | 规范化后的节点集合 |
| `All` | 当前租户全部数据 | 审计管理员 | 只保留租户过滤 |

默认值必须是 `None`，不能使用 `All`。保存 `Custom` 时应执行规范化：

- 如果父节点已包含下级，移除其后代节点，减少重复规则。
- 拒绝其他租户、已删除或不存在的节点。
- 对停用节点给出警告；是否允许保留由业务策略决定。
- 空的 `Custom` 等价于 `None`。

## 五、权限合并规则

### 5.1 多角色

现有 RBAC 以允许权限为主，本设计第一阶段不引入显式拒绝规则，以免产生难以解释的“允许与拒绝优先级”。

- 功能权限：用户所有有效角色的并集。
- 同一资源的数据范围：拥有该资源功能权限的角色范围并集。
- 字段策略：读取采用并集，写入采用更严格的交集或独立写权限。
- `All` 只在拥有对应资源功能权限时生效，不能绕过功能权限。
- 超级权限 `*:*:*` 可跳过功能权限检查，但数据范围是否也跳过必须由单独的系统策略明确配置；建议仅 Host 管理员可全局跳过。

不能用枚举大小比较范围强弱，因为 `Custom(A, B)` 与 `OrganizationAndDescendants(C)` 未必可比较。合并结果应先展开为组织集合或可组合查询表达式。

### 5.2 多组织成员关系

`AnchorMode` 明确决定范围从哪里开始：

- `PrimaryOrganization`：仅主组织，默认且最易解释。
- `AllMemberships`：主组织与所有有效兼职组织。
- `FixedOrganizations`：与用户成员关系无关，由角色配置固定节点。

不得把兼职组织隐式加入主组织范围。管理员在保存时必须能看到实际起始节点。

### 5.3 写操作

读取范围不能自动等于写入范围。写入至少校验：

1. 用户拥有该操作的功能权限。
2. 目标记录位于写数据范围内。
3. 新归属组织处于用户可创建范围内且为启用状态。
4. 跨组织移动使用独立权限，例如 `resource:transfer`。
5. 请求中的 `OrganizationUnitId`、`OwnerUserId` 不允许被普通 DTO 批量赋值绕过。

## 六、后端判定流程

可编辑流程图见 [`diagrams/organization-permission-flow.mmd`](../../diagrams/organization-permission-flow.mmd)，已验证的预览见 [`diagrams/organization-permission-flow.svg`](../../diagrams/organization-permission-flow.svg)。领域关系图源与预览分别位于 [`diagrams/organization-permission-er.mmd`](../../diagrams/organization-permission-er.mmd) 和 [`diagrams/organization-permission-er.svg`](../../diagrams/organization-permission-er.svg)。

服务入口不要自行拼接组织条件。建议提供稳定的应用层端口：

```csharp
public interface IDataScopeResolver
{
    Task<DataScopeDecision> ResolveAsync(
        Guid userId,
        string resource,
        string action,
        CancellationToken cancellationToken = default);
}

public interface IDataScopeFilter
{
    IQueryable<TEntity> Apply<TEntity>(
        IQueryable<TEntity> query,
        DataScopeDecision decision)
        where TEntity : IOrganizationOwned;
}
```

`DataScopeDecision` 至少包含：

- 是否具有功能权限。
- 规范化范围类型。
- 允许的组织节点或路径前缀。
- 是否允许本人数据。
- 产生结论的角色和策略 ID。
- 策略版本，用于缓存和审计。

业务查询的推荐顺序：

1. 应用租户过滤。
2. 验证功能权限。
3. 解析并应用数据范围表达式。
4. 应用资源自身状态和共享策略。
5. 投影 DTO，并按字段策略隐藏或脱敏。
6. 记录拒绝、跨组织写入和权限配置变更审计。

## 七、权限预览

“查看最终权限”是这个系统是否清晰的关键能力。预览接口接收：

- `SubjectType`：用户或角色。
- `SubjectId`。
- `Resource` 与 `Action`。
- 可选 `OrganizationUnitId` 或具体业务记录 ID。

返回结果应面向解释，而不是只返回 `true/false`：

```json
{
  "allowed": true,
  "summary": "可查看华东区及其 12 个下级组织的数据",
  "scopeType": "OrganizationAndDescendants",
  "organizations": 13,
  "sources": [
    {
      "role": "区域经理",
      "reason": "从主组织“华东区”起算并包含下级"
    }
  ],
  "warnings": []
}
```

预览结果必须标记为“按当前策略计算”，不能作为后续请求的授权凭证。真实业务请求仍需重新判定。

## 八、建议 API

### 8.1 组织

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/system/organization/tree` | 按需加载组织树 |
| `GET` | `/api/system/organization/{id}` | 节点详情、成员和风险摘要 |
| `POST` | `/api/system/organization` | 新建组织 |
| `PUT` | `/api/system/organization/{id}` | 编辑基础信息 |
| `POST` | `/api/system/organization/{id}/move` | 移动节点，要求版本和影响确认 |
| `POST` | `/api/system/organization/{id}/disable` | 停用节点 |
| `PUT` | `/api/system/organization/{id}/members` | 批量维护成员关系 |

### 8.2 数据范围

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/system/data-scope/roles/{roleId}` | 读取角色的资源范围 |
| `PUT` | `/api/system/data-scope/roles/{roleId}/{resource}` | 保存一个资源范围 |
| `POST` | `/api/system/data-scope/preview` | 解释最终权限 |
| `GET` | `/api/system/data-scope/resources` | 返回可配置资源及动作 |

所有写接口使用稳定业务错误码、中英文资源、乐观并发版本和审计记录。批量成员变更、移动组织和扩大数据范围应记录变更前后摘要。

## 九、缓存与一致性

- 组织树可以按 `TenantId + OrganizationVersion` 缓存。
- 用户最终策略可以按 `TenantId + UserId + PermissionVersion` 缓存。
- 角色、成员关系、组织路径或数据范围变化时递增版本并失效缓存。
- 不建议只依赖短 TTL；权限收缩后必须尽快失效，避免离职、调岗或角色回收后继续访问。
- 后台任务、导出和消息消费者必须显式恢复租户与用户授权上下文，不能绕过数据范围。

## 十、审计与安全

必须审计：

- 组织新增、重命名、移动、停用和删除。
- 主组织与兼职关系变化。
- 角色功能权限和数据范围变化。
- 权限预览中的高风险模拟。
- 被拒绝的跨组织读取和写入。
- 导出、批量操作和字段解密。

审计记录不保存敏感字段明文，只保存主体、资源、动作、范围摘要、策略版本、结果和关联 ID。

## 十一、实施阶段

### 第一阶段：可解释的组织与数据范围基线

- 组织树、主组织和兼职关系。
- 六种数据范围类型。
- 角色按资源配置范围。
- 统一解析器和查询过滤器。
- 最终权限预览。
- 配置变更审计。

### 第二阶段：业务接入

- 为选定业务实体补齐 `OrganizationUnitId` 和 `OwnerUserId`。
- 接入列表、详情、导出、更新和跨组织移动。
- 增加真实数据库集成测试和越权矩阵。

### 第三阶段：字段与临时授权

- 字段隐藏、脱敏和编辑策略。
- 有效期授权、代理审批和紧急访问。
- 权限影响分析与回收建议。

## 十二、完成定义

- 组织不能形成环，移动后全部后代路径一致。
- 每个用户最多一个有效主组织。
- 新角色默认无数据，不会意外获得全租户范围。
- 任意业务列表、详情、导出和写入使用同一数据范围解析器。
- 多角色、多组织和 `Custom` 范围的合并有确定规则和测试。
- 前端能够解释允许或拒绝的来源，颜色不是唯一提示。
- 权限收缩后缓存能主动失效。
- 组织和范围变更有审计、并发控制、迁移和回滚方案。
- Web 在 375、768、1024 和 1440 px 下可用，键盘可以完成选择、预览和保存。
- 后端具有跨租户、跨组织、本人、下级、停用组织、空范围和超级管理员测试矩阵。

## 十三、明确不做

第一阶段不包含：

- 把汇报线、项目组、成本中心和法定实体全部塞进同一棵树。
- 前端自行过滤数据。
- 通过组织负责人身份自动授予权限。
- 隐式的显式拒绝规则。
- 将权限预览结果作为后续请求的授权票据。
- 未经业务确认自动迁移员工调岗前的历史数据归属。
