# 企业级系统建设与演进指南

## 本地开发环境基线

开放平台已恢复为平台模块：应用凭据由 Data Protection 加密，创建或重置时仅展示一次；Scope 在服务端按可授予权限目录校验，client_credentials 令牌仅能访问带显式 `[Permission]` 的端点，签发与携令牌调用均留审计。存量站点需先执行受控迁移，再运行种子补齐模块、权限和菜单；验收需覆盖凭据错误、保留 Scope 拒绝、IP 白名单、令牌权限与审计记录，不能只验证菜单可见。

Windows WPF Client 已具备 API 连接、账号登录与双重验证、账号安全（改密、双重验证启停、登录会话、账号注销）、工作台、个人资料、通知、审批中心（待办/已办/我提交/抄送/流程定义/实例监控、详情、时间线、附件和同意/驳回/转交/加签/退回/撤回/重新提交/催办/终止）、授权管理（用户重置密码与角色分配、角色模块/权限分配）、系统管理（组织架构、租户启停、字典项、系统配置、定时任务、文件存储配置、通知渠道/模板/规则/Webhook），以及四套风格 × 明暗的桌面入口；主题偏好与 Web 共用后端配置。桌面 UI 建立自建的 Naive UI 复刻控件库（表单、展示、容器、浮层四族，样式集中在 `Theme/Controls.*.xaml`），全端不使用投影，层级只由 2px 描边、圆角与语义色表达，并通过 `--gallery` 预览窗口验收组件外观。审批动作按待办权限判断并要求用户确认。桌面端 Access Token、Refresh Cookie 和密码不落盘，关闭程序后重新登录；401 后经 CSRF 保护的 Refresh Cookie 刷新并只重试一次。本地联调需验证受信任 TLS 证书、普通及双重验证登录、刷新失败后的重新登录、改密后的重新登录、双重验证启停、会话注销、审批动作权限、附件上传下载、流程定义草稿新建/筛选/原生画布新增和拖动节点/悬停显示四边连接点/拖动时连接点跟随/三种线型切换/节点和连线编辑/保存/校验/发布/停用/升版、用户/角色/租户/字典项操作、定时任务、存储连通性、通知保存与测试、CSRF 注销、组件库预览和八种配色。WPF 客户端提供业务模块装配入口：业务在 `client/<业务>/` 实现 `IBusinessClientModule`，源码经 `BusinessSources.props` 纳入基座工程编译，菜单与懒加载标签页由基座装配，基座同步冲突限制在 `BusinessModuleRegistration.cs` 与 `BusinessSources.props` 两个组合根文件。E2EE/通行密钥和外部登录绑定仍待原生 WPF 复刻，当前不以 Web 页面嵌入掩盖缺口；这些缺口不改变后端认证契约、部署拓扑或既有风险优先级。

`api/env/compose.yaml` 提供 PostgreSQL、Redis、RabbitMQ 的单实例开发环境，包含健康检查、回环端口绑定与持久化命名卷；API/Web 在宿主机运行。默认公开凭据仅用于本地开发，首次初始化和数据删除步骤见 [本地开发基础设施](../ops/LOCAL_INFRASTRUCTURE.md)。该配置不替代生产密钥管理、备份恢复或高可用验收，不改变现有生产风险优先级；容器运行验证需在安装 Docker 的环境执行。

命名基线：程序集与命名空间统一为 `Sim.*`，解决方案为 `api/Sim.slnx`，数据库表前缀为 `sim_`（Quartz `sim_qrtz_`），镜像与环境变量为 `sim-api` / `sim-web` / `SIM_*`，DataProtection 应用名为 `SimApp`。DataProtection 应用名与用途串属于密文解密契约，改名会使历史密文不可读，升级前必须迁移或重录相关密钥。旧命名基线的数据库、密钥环与 E2EE 密文与当前基线不兼容，升级按重建或迁移处理。

本文档结合 SimApp 当前架构，总结从新项目立项到生产运行需要考虑和实现的内容。它既是经验清单，也是持续演进基线：后续每次功能增强、缺陷修复、依赖升级或部署调整，都必须判断是否改变了本文档中的决策、风险、完成标准或现状清单。

本文档不要求所有项目都采用微服务、容器编排、多租户或复杂中间件。企业级的核心不是技术数量，而是业务边界清楚、安全风险受控、数据可恢复、变更可验证、运行可观测、故障可处理。

## 如何使用本文档

开始需求或修复前：

1. 判断变更影响哪些质量属性：安全、正确性、可用性、性能、可维护性、兼容性、合规或成本。
2. 检查对应章节是否已有约束，是否需要新增架构决策记录（ADR）。
3. 明确验证方式、上线方式、兼容策略和回滚方式。

完成变更前：

1. 使用“变更触发矩阵”和“完成定义”复查。
2. 如果实现状态、接口契约、部署要求或风险发生变化，在同一次变更中更新本文档。
3. 即使不需要更新，也应在评审或交付说明中明确写出“已检查，无需更新”及原因。

状态标记建议：

- `已具备`：有实现、有验证，并进入日常维护。

- `部分具备`：已有基础实现，但缺少覆盖、自动化或生产验证。

- `待建设`：尚无可靠实现。

- `不适用`：经过明确决策，本系统当前不需要；应记录判断依据和复审条件。

## 一、业务目标与约束

技术设计前应先形成可验证的业务输入：

- 目标用户、核心业务流程、系统边界和不做的内容。

- 关键数据的所有者、敏感级别、保存周期和删除要求。

- 峰值用户数、吞吐量、数据规模、地域和终端类型。

- 可用性目标（SLO）、恢复时间目标（RTO）和恢复点目标（RPO）。

- 法律、行业、审计、隐私、知识产权和数据驻留要求。

- 预算、人员能力、交付周期及允许的运维复杂度。

应产出的最小文档：

- 业务上下文图和主要用例。

- 领域术语表。

- 非功能需求清单。

- 关键风险和假设。

- 重要架构决策记录（ADR）。

## 二、系统边界与架构设计

### 模块边界

- 先按业务能力拆分模块，再决定部署单元；模块化单体通常比过早微服务更合适。

- 业务模块对外提供 Contracts、事件或明确的应用接口，不依赖其他模块的实现层。

- 通用 framework 不能反向依赖 `system`、`approval` 等业务模块。

- 平台模块通过 `IModuleSeedContributor` 自描述模块、权限、路由与数据种子，平台种子只汇总贡献者，不在 Admin/Host 中反向引用具体模块；审批作为平台模块同样走该机制。

- 权限、审计、时钟、当前用户、文件存储等跨模块能力应定义稳定抽象，避免所有模块直接引用某个业务领域项目。

- 空模块、占位项目和重复分层应有明确启用计划；长期无职责的项目应合并或删除。

依赖方向应保持为：

```text
Host / Composition Root
        ↓
Application → Application.Contracts
        ↓              ↓
      Domain → Domain.Shared
        ↑
Infrastructure / SqlSugar（实现 Domain 中的端口）
```

### 架构决策

以下情况通常需要 ADR：

- 单体、模块化单体或微服务的选择。

- 数据库、消息系统、缓存、搜索和对象存储的选择。

- 身份认证、租户隔离和权限模型。

- 同步调用与异步事件的边界。

- 前端模块化、动态路由和部署方式。

- 需要长期维护的第三方平台集成。

### 避免过度设计

- 不因“将来可能需要”引入无法验证的抽象。

- 不为只有一个实现的简单逻辑创建多层转发。

- 不把配置驱动和编译期模块注册同时作为两个事实来源。

- 新增依赖前说明用途、替代方案、维护状态、安全记录和移除成本。

## 三、API 与契约

- 接口使用统一路径、HTTP 语义、分页、排序、过滤和错误格式。

- 对外或跨团队 API 应有版本策略，明确兼容窗口和废弃流程。

- DTO 只包含调用方需要的数据；内部密钥、Refresh Token、数据库字段和审计字段不得因复用实体而泄漏。

- 公开资料按最小披露原则拆分 DTO：公开接口只返回业务需要的展示字段，邮箱、电话、地址、认证字段和内部标识不得出现在匿名可读响应中；个人更新接口只能修改当前登录用户的数据，头像必须通过上传接口产生，不接受外部 URL。

- 输入验证在边界执行，领域规则仍由领域层保证。

- 写接口考虑幂等键、重复提交、乐观并发版本和冲突响应。

- 长任务使用异步任务模型，不让 HTTP 请求无限等待。

- OpenAPI 是契约之一，应在 CI 中检查破坏性变更；前端类型宜由契约生成或进行契约测试，减少手写类型漂移。

- Swagger/OpenAPI 文档面默认只在非生产环境注册；Production 必须显式设置 `Swagger:AllowInProduction=true` 才开放。Docker/nginx 同域部署通过反向代理暴露 `/swagger/`，并用 Basic Auth 保护 `/swagger/` 与 `/api/swagger-config`。文档面不得被当作授权依据，业务接口必须在自身端点独立校验 JWT Bearer 和权限。对外交付契约应提供单个聚合文档，便于工具一次性导入，避免按模块逐个接入造成遗漏。

- 错误响应包含稳定错误码和关联 ID，不向客户端暴露堆栈、SQL、文件路径或内部类型名。

## 四、身份、安全与隐私

### 身份与权限

- 明确用户、服务账号、机器身份和管理员身份的生命周期。

- 删除用户必须清理账号级数据并处理业务归属：外部登录绑定、刷新令牌、组织成员与负责人引用、存储配额、分享链接和用户偏好必须硬删除；审批实例、审批记录等需要留痕的业务事实不得随账号硬删除，应保留业务数据并解除或匿名化个人关联；跨模块清理通过 `IUserDeletedHandler` 端口在同一删除事务内执行，由各业务模块声明自身清理或匿名化策略，任一处理器失败必须整体回滚。自助注销必须重新校验当前密码，并复用同一清理/匿名化流程与内置账号保护，不得提供绕过密码校验的注销入口。

- 优先使用经过评审的标准身份协议和实现（如 OAuth 2.0/OIDC 或 BFF），使用短期 Access Token；长期凭据采用可撤销、可轮换机制。

- 浏览器直接调用 API 且采用 Refresh Token Cookie 时，令牌只保存在受限的 HttpOnly Cookie，服务端只保存哈希，并实现轮换和重放检测；其他客户端按其威胁模型选择安全存储。

- 使用 Cookie 作为认证或刷新边界时，同时考虑 `Secure`、`SameSite`、作用域和 CSRF。

- “记住我”类能力只允许延长可撤销的会话凭据，或把密码交给浏览器/操作系统凭据库保存；不得在 `localStorage`、`IndexedDB` 等脚本可读位置持久化明文密码，前端自加密也不能替代凭据库。

- 权限必须在后端执行；前端菜单隐藏只能改善体验，不能作为安全边界。

- 外部登录采用后端代理式接入：提供方 token 不进入前端；一次性 state 使用 Data Protection 加密的 HttpOnly Cookie 并保存登录/绑定意图，统一回调端点按意图执行登录、关联已有账号、注册新账号、2FA 或绑定，`system_external_login` 只保存稳定 provider key，已绑定用户的 2FA 不被绕过。未绑定身份必须先在本系统口令校验通过的已有账号与新建账号之间显式选择，系统仍不依据 email 自动关联。新建账号受站点配置 `security.registration-enabled` 约束：开关关闭时回调不再拒绝，而是返回令牌并标记 `ExternalLoginRegistrationAllowed=false`，只保留关联已有账号入口；补齐端点仍需再次校验该开关并拒绝创建。

- 自助注册（含第三方登录补齐）的用户角色必须由后端系统配置 `security.registration-role-codes` 决定，禁止接受客户端提交的角色参数；只允许非内置角色，内置管理员角色不得通过注册配置下发。默认 `User` 角色应在种子中补齐基本权限与端用户模块，管理员仍需在角色管理中复核其权限范围。

- 高风险操作考虑二次认证、审批、操作原因和审计追踪。

- 管理员、服务账号和默认账号必须支持首次使用改密、禁用、吊销和定期复核。

- 内置角色/账号标记只用于宿主级身份。租户管理员不得复用内置角色标记获得全局权限绕过，权限判定必须同时确认调用方无租户归属；租户管理员只能获得租户内显式授予的权限。初始化时创建的管理员与 `system` 账号均为内置账号：账号名与角色分配不可变，禁止删除，昵称、邮箱等资料仍可编辑。

- 登录失败计数、验证码尝试次数等安全状态必须在独立事务中持久化，业务异常回滚不得撤销安全计数；账号锁定与会话撤销都需要可验证的触发与恢复路径。

### 密钥与配置

- 源码、镜像、日志、测试数据和文档中不得存在可用的默认密码、生产密钥或真实连接串。

- 密钥来自环境注入、密钥管理服务或受控挂载，并支持轮换。

- 启动时验证必需配置；缺少安全配置时应快速失败，而不是退回弱默认值。

- 运行期可编辑的品牌、站点名称、TOTP 发行方、验证码与认证器有效期、通知服务商显示名放入系统设置或数据字典；DataProtection、JWT、E2EE、SMTP/SMS 凭据及部署标识保留配置文件或环境变量。

- 开发环境示例账号不得使用众所周知的固定密码；共享开发环境必须按生产原则管理账号。

#### 密钥管理分级方案

密钥方案按部署规模演进，不要求单台内网服务器一开始就建设复杂密钥集群：

| 场景                           | 推荐方式                                                           | 最低安全要求                                                                                                                  |
| ------------------------------ | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| 本地开发                       | .NET User Secrets 或当前进程环境变量                               | 不进入仓库、共享脚本、日志和截图；不得复用生产值                                                                              |
| 单台或少量内网服务器           | 操作系统权限保护的独立 Secret 目录，通过 .NET `AddKeyPerFile` 读取 | 目录位于发布目录外；运行账号只读；Linux 文件权限不高于 `600`，Windows 使用独立服务账号和 NTFS ACL；备份单独加密和授权         |
| Docker Swarm                   | Docker Secrets 挂载到 `/run/secrets`，应用使用 `AddKeyPerFile`     | 使用 Swarm 原生 Secret；普通 Compose 的源文件仍按宿主机 Secret 文件保护；Secret 不写入镜像、Compose 正文或命令行              |
| Kubernetes                     | Secret 只读 Volume，或由外部 Secret Operator/Agent 写入内存卷      | 开启 etcd 静态加密、最小权限 RBAC、独立 ServiceAccount/Namespace；Base64 不是加密                                             |
| 多服务器、多系统或需要集中审计 | 内网自建 OpenBao、Infisical 或经过评审的等效产品                   | 密钥中心与业务主机分离；内网 TLS；机器身份和短期令牌；最小权限策略；访问审计；高可用、加密备份、恢复演练和解封/根凭据分离保管 |
| 公有云托管                     | Azure Key Vault、AWS Secrets Manager 或对应云原生服务              | 使用托管身份/工作负载身份，避免长期访问密钥；按应用和环境隔离权限并开启审计                                                   |

内网部署优先选择开放标准和可离线运维的方案。OpenBao 适合需要策略、审计、租约、动态凭据和集中轮换的团队；Infisical 提供较完整的自托管界面和机器身份能力。密钥中心本身会引入 TLS、存储、初始化/解封、备份、升级和灾备责任：若密钥中心与应用运行在同一台服务器，不能抵御该服务器管理员或 root 被攻破，只能降低源码、镜像和发布包泄漏风险，因此小规模系统优先使用受控文件通常更合理。

#### 应用接入约定

- 应用继续通过标准 `IConfiguration`/Options 读取密钥，业务模块不得直接读取文件、环境变量或调用具体密钥厂商 SDK。

- 环境变量使用双下划线表示层级，例如 `JwtSettings__IssuerSigningKey` 映射为 `JwtSettings:IssuerSigningKey`。

- 文件注入统一采用 Key-Per-File：文件名使用 `JwtSettings__IssuerSigningKey`，内容为密钥值；Secret 根目录只允许使用绝对路径，并由启动参数或非敏感环境变量指定。

- OpenBao/Infisical 优先通过 Agent、Sidecar 或 Operator 使用机器身份取得短期令牌，并把 Secret 渲染到受控文件/内存卷；避免在业务进程中维护根令牌、续租和供应商协议。

- 所有必需 Secret 在应用接受流量前完成存在性、长度、格式和可访问性校验；不得因密钥中心暂时不可用回退到源码默认值。

- 不记录密钥内容、Secret 响应、环境变量集合、挂载目录内容或认证令牌；健康检查只报告依赖是否可用，不泄露路径和标识。

#### 轮换与恢复

- 每个密钥必须记录所有者、用途、作用域、创建时间、轮换周期、吊销方式和受影响系统，不使用一个密钥跨开发、测试、生产环境。

- 轮换采用“新增密钥—双密钥验证—切换签发—等待旧凭据过期—撤销旧密钥”的重叠窗口；应用和协议不支持双密钥时，必须明确维护窗口、强制重新登录和回滚步骤。

- JWT 已支持 `kid` 多密钥平滑轮换，并可选使用 SM2 国密非对称签名（`JwtSettings:SigningKeys[*]:Algorithm=SM2WITHSM3`）；切换签发密钥时必须保留旧密钥可验证直到旧 Token 过期，不能把密钥管理工具的“修改值”误认为无中断轮换。

- 密钥中心故障、密钥误删、权限策略错误、证书过期和主机重建必须有 Runbook；备份恢复演练需要同时验证密文存储、解密/解封材料、策略、审计配置和应用重新取密能力。

密钥方案的完成定义：生产值不进入仓库/镜像/普通配置文件；应用使用独立机器身份或服务账号按最小权限读取；缺失密钥启动失败；存在可执行轮换和恢复步骤；访问可审计；已验证密钥替换后的会话影响与回滚。

### 应用安全

- 建立威胁模型，至少覆盖认证绕过、越权、XSS、CSRF、SQL 注入、SSRF、文件上传、路径穿越、反序列化和供应链风险。

- 浏览器端设置 CSP、HSTS、Referrer-Policy、Permissions-Policy 等安全头，并避免不受控 `v-html`。

- HTML/Markdown 渲染必须净化，并对 URL 协议、图片源和附件做限制。

- 限流应区分登录、验证码、公开写接口和高成本查询；会话维护接口（刷新、吊销）使用独立分区，避免被匿名流量挤占而被迫重新登录或无法注销；多实例部署使用共享限流或网关限流。

- 反向代理头只信任明确配置的代理，避免伪造客户端 IP 影响审计和限流。

- 依赖升级需要漏洞扫描、许可证检查、SBOM 和修复时限。

### 数据与隐私

- 数据按公开、内部、敏感、受监管分级。

- 明确采集目的、最少化、脱敏、导出、删除和保留策略。

- 敏感数据传输和静态存储加密，并记录密钥轮换与恢复方式。

- 日志、指标、追踪和审计中禁止记录密码、Token、Cookie、证件号等敏感值。

- 系统只提供身份层 E2EE 能力（`system_user_e2ee_identity`、`system_user_e2ee_passkey`），不包含任何业务实体的服务端解密路径；业务模块启用端到端加密时复用该身份与解锁面板，在自身契约中扩展密文字段，并实现业务守卫供身份重置判定。

- 框架 E2EE（`web/src/e2ee/`）只保留通用密钥、信封、文件、设备缓存与通行密钥能力，不包含具体业务实体类型、AAD 或分享协议；文章/内容加密、密文兼容标识和分享流程放在业务区，并通过 `configureE2eeProfile` 固定历史格式。发现业务类型进入框架 E2EE 时按架构缺陷处理。

- E2EE 按“服务端不持有可解密密钥”验收：加密口令、UMK、ACK、恢复密钥只在浏览器内存/用户离线文件中，服务端仅保存 KDF 参数与 `wrap:v1` 包裹密钥；禁止新增服务端解密、导出或后台回填明文的路径。标题等可见元数据边界由启用该能力的业务模块在设计文档中声明。

- E2EE 密钥丢失不可由平台恢复：忘记加密口令且丢失离线恢复密钥即永久不可读。已取消登录密码 RK 备份；升级清除旧备份字段，旧客户端不得重新创建备份。账号密码重置不能恢复 E2EE。旧数据库备份中的密钥包裹不能被远程收回，需按备份保留策略处理。

- 分享链接是 bearer capability：撤销时必须轮换访问凭证和文件密钥，旧凭证不能读取当前版本；已下载副本不在撤销范围内；日志不得记录完整链接、口令、UMK/ACK/RK 或正文。

- E2EE 设备便利能力按“可撤销、可手动清除”验收：本机“信任此设备”缓存不设自动有效期，退出登录即删除，并提供“遗忘本机”入口；设备缓存通过不可导出 CryptoKey 保护 UMK，不得包含原始密钥，必须写明其不能抵御同源脚本、恶意扩展或配置文件复制。

- 无受保护业务数据时允许重置 E2EE 身份：浏览器生成全新 UMK、RK、salt 与新口令包裹，调用 `POST /api/system/e2ee/reset-identity`；服务端必须通过 `IUserE2eeArticleGuard` 端口查询业务模块登记的加密数据数量（裁剪基线为 `NoopUserE2eeArticleGuard`，始终视为 0），存在受保护数据时返回 `UserE2eeIdentityResetBlocked` 并 fail-closed，不得只靠前端隐藏入口。业务模块接入加密后必须替换为真实守卫，并增加清除旧设备缓存与强制用户离线保存新恢复密钥的验收。

- 通行密钥解锁必须记录 PRF 与普通 WebAuthn 签名的区别：服务端仅保存公开凭证和 UMK 密文，按当前账号/租户/UMK 版本隔离，固定 RP ID/Origin，userVerification=required，挑战原子单次消费并验证过期/重放/签名/userHandle；PRF 材料不得上网，取消验证不解锁；保留口令/RK 回退，域名变更、解绑与身份重置边界必须写明；虚拟认证器通过不能等同于真实硬件联调完成。

## 五、数据架构与一致性

- 生产数据库结构使用可追踪的版本化迁移，记录执行历史和校验结果。

- 迁移采用向前兼容的 expand/migrate/contract 策略，支持滚动发布。

- 上线前明确备份、恢复和回滚方式；定期做恢复演练，不能只确认“备份任务成功”。

- 多写操作使用清晰事务边界，外部调用不能长期占用数据库事务。

- 跨模块或跨服务一致性优先使用 Outbox/Inbox、幂等消费者和补偿流程，不使用不可控的分布式事务。

- 重要表必须使用统一审计字段（创建人、创建时间、修改人、修改时间），并考虑并发版本、唯一约束、软删除策略和归档策略；仅追加日志、关联记录与不可变快照可只保留创建审计，但必须在模型中说明豁免原因。

- 查询建立容量基线、索引策略、慢查询阈值和分页上限。

- 多租户只有在业务确实需要时引入；一旦引入，必须覆盖数据隔离、缓存键、任务、审计、备份和管理员越权风险。

- 租户上下文必须在认证完成之后解析，并在仓储的全部读写路径（含按主键查询、更新、删除）应用；登录、刷新和会话校验必须拒绝已删除或已停用的租户。删除租户必须级联处理租户用户、角色、授权关系和会话，不能留下可登录的孤儿账号。租户内用户名/登录名必须保持全局唯一，避免登录解析歧义。

## 六、后台任务与外部集成

- 任务必须幂等，明确重试次数、退避、超时和不可重试错误。

- 生产任务调度使用持久化存储；多实例下明确单实例执行、分片或并行策略。

- 失败任务进入可查询的失败记录或死信队列，并提供重放和人工处理流程。

- 外部调用设置连接超时、请求超时、重试、熔断和隔离，避免级联故障。

- Webhook 验证签名、时间戳和重放，并保存处理幂等键；未配置签名密钥时必须失败关闭，不能默认接受匿名写入。

- 重要集成建立契约测试和沙箱环境。

## 七、前端工程

- 业务页面、API、类型和路由按模块组织，公共层不反向依赖具体业务模块。

- 框架共享组件不得 import 业务模块；业务差异通过框架端口（例如导出适配器）、路由元数据或业务区封装接入，不直接修改框架组件内部。

- Web 应用壳（`createApp`、平台模块、路由与请求层）以库模式（`pnpm build:lib`）复用；业务应用拥有入口，并负责注册自己的页面 glob 与按需语言包，框架源码不得扫描业务目录。

- 登录、401 刷新、退出、路由守卫和动态路由只有一个明确状态机，避免多处各自恢复会话。

- Access Token 不进入持久化存储；刷新凭据不可被 JavaScript 读取。

- 后端返回类型与前端模型通过生成或契约测试保持一致。

- 建立统一错误展示、加载、空状态、权限不足和离线处理。

- 表单校验时机必须明确：必填、长度和格式在失焦时提示并在提交时复验；唯一性在输入时防抖查重；跨字段一致性在依赖字段变化时复验；文件、复杂条件配置和画布类表单在提交时校验。界面上的必填标记必须对应真实规则，前端查重不能替代后端唯一约束。提交校验失败时必须把第一个错误字段滚动到可视区域并聚焦，字段区内部滚动的弹窗与页面同样适用。

- 视觉基线统一在单一设计系统内：Web 使用 Paper Ocean 令牌（奶油纸底、2px 描边、硬投影、电光蓝强调、珊瑚主行动）；Web 另提供玄青·鎏金、竹月·清雅、朱缃·典章 3 套商务风格，4 套风格 × 明暗全部从 `src/config/themes.ts` 注册表派生，商务结构差异只由 `business-skin.css` 承担，页面只消费 `--po-*` 变量与 `.po-*` 组件类；新增页面上线前在 4 套风格 × 明暗与移动宽度下自检；规范见 `docs/design/ui/IMPLEMENTATION.md` 与 `docs/design/ui/MULTI_THEME_DESIGN.md`。

- 满足键盘操作、焦点、语义标签、对比度和屏幕阅读器等可访问性要求。

- 支持国际化时，从文案、日期、数字、时区和排序规则一起设计。

- 客户端语言通过标准 `Accept-Language` 传递；后端业务错误使用稳定错误码和服务端资源生成展示文本，客户端为已知错误码、HTTP 状态和离线场景保留本地降级文案。

- 设置性能预算：首屏资源、主包大小、路由分包、图片、字体和长列表。

- 调试日志、示例模块、Mock 数据和开发工具不得进入生产路径。

- 对 `v-html`、富文本、Markdown、文件预览和外链建立统一安全封装。

## 八、可靠性、可观测性与运维

### 健康与韧性

- 分开提供 liveness、readiness 和必要的启动探针。

- readiness 检查关键依赖，但避免每次探针执行高成本业务查询。

- 支持优雅关闭，停止接收新流量后完成或安全中断在途任务。

- 明确超时、重试、熔断、舱壁、降级和容量保护策略。

- 后台服务必须隔离瞬时依赖故障：轮询循环内部捕获异常并记录日志，Host 配置 `BackgroundServiceExceptionBehavior=Ignore`；数据库连接池耗尽或短暂不可用不得终止 API 进程。

- 为缓存、数据库、队列和外部服务定义不可用时的行为。

### 可观测性

- 日志使用结构化字段，包含请求/关联 ID、用户匿名标识、模块、错误码和耗时。

- 指标至少覆盖流量、错误、延迟、资源饱和度，以及登录失败、任务失败等业务指标。

- 分布式场景接入 Trace，并在日志、指标和 Trace 之间保留关联。

- 建立告警分级、抑制、值班、升级和复盘机制，避免只有错误日志没有行动路径。

- 为常见故障编写 Runbook：数据库不可用、证书过期、密钥轮换失败、队列积压、登录异常、磁盘不足等。

### 灾备

- 按 RTO/RPO 设计备份频率、跨区域副本和恢复流程。

- 定期演练数据库、对象存储、密钥和配置的联合恢复。

- 灾备文档必须包含负责人、权限、依赖、验证标准和恢复后的数据校验。

## 九、构建、供应链与交付

- 固定 .NET SDK、Node.js 和包管理器版本，提交锁文件。

- 已评审并提交的前端锁文件可以作为可信重复安装基线；新依赖解析和版本升级仍需执行发布等待期、漏洞和许可证检查，锁文件变更必须进入代码评审。

- .NET 包版本使用集中式管理，减少项目间版本漂移。

- 文本文件通过 `.editorconfig` 与 `.gitattributes` 统一行尾：普通文本使用 CRLF，Linux 脚本类文件使用 LF；提交前不得出现 `w/mixed`。

- CI 至少执行格式/静态检查、编译、类型检查、单元测试、集成测试、安全扫描和生产构建。

- 主分支不得长期容忍红色质量门禁；临时例外需要负责人、原因和清理日期。

- 容器使用与目标框架一致的受支持基础镜像，多阶段构建、非 root 运行、只复制发布产物，不在镜像中生成或硬编码生产证书。

- 构建产物应可重复、可追踪，包含版本、提交号和 SBOM，并进行镜像/制品签名与漏洞扫描。

- 环境差异只来自外部配置，不为不同环境编译不同业务逻辑。

- 发布支持数据库先行兼容、灰度或蓝绿、自动健康验证和可执行回滚。

- Feature Flag 有负责人、默认值、审计和清理日期，不能成为永久分支。

## 十、测试策略

当前基线风险：`web/src` 下的前端单元测试已全部删除，登录、权限、动态路由、加密和组件状态等回归覆盖缺失，且单元测试质量门禁可能因没有测试用例而失败。此项按高优先级恢复；完成定义为恢复关键组件与状态测试，并在 CI 中执行通过。

最低测试组合：

- 单元测试：领域规则、权限、转换、状态机和边界条件。

- 集成测试：数据库仓储、事务、迁移、认证 Cookie/CSRF、任务和外部适配器。

- API 契约测试：路径、状态码、错误码、DTO 和兼容性。

- 前端组件/状态测试：登录、刷新并发、退出、权限和动态路由。

- 端到端测试：最关键用户旅程，而不是脚手架默认页面。

- 安全测试：越权、弱配置、输入攻击、依赖漏洞和密钥泄漏扫描。

- 性能测试：基线、峰值、长时间稳定性和容量拐点。

- 恢复测试：备份恢复、迁移回滚、任务重放和灾备切换。

测试数据应可重复构造并与生产数据隔离。测试失败不能通过删除测试、关闭规则或降低断言来解决。

- Pull Request 使用统一检查清单，并要求安全或架构高风险变更由对应负责人评审。

DataProtection 运维基线：`DataProtection:KeysPath` 必须持久化、限制访问并独立备份；多实例共享同一密钥环和 `DataProtection:ApplicationName`。丢失密钥环会使依赖它的历史受保护数据不可恢复，迁移失败必须阻断启动。

设备信任完成定义补充：IndexedDB v3 新记录由不可导出 CryptoKey 直接保护 UMK，不得包含原始 UMK 或 deviceKey，CryptoKey 必须不可导出；旧记录读取时迁移，失败清除，不做裸密钥兜底。验证事务提交、锁定期间读取取消及当前页面清除期间写入取消；验证真实浏览器刷新后仍可解锁。风险边界仍包含 XSS、扩展和配置文件复制，不新增空闲过期或远程设备吊销；WebAuthn PRF 作为可选解锁方式已接入，见下述完成定义。

通行密钥完成定义：服务端仅保存公开凭证和 UMK 密文，严格按当前账号/租户/UMK 版本隔离，固定来源配置，userVerification=required，挑战原子单次消费并验证过期/重放/签名/RP/Origin/userHandle。前端 PRF 材料不得上网；在本浏览器选用通行密钥时清除既有自动缓存，取消验证不解锁；存在受信任设备缓存时优先用缓存静默解锁，通行密钥作为无缓存时的显式方式；保留口令/RK 手动解锁。身份重置清理凭证/挑战，解绑不承诺收回已获取 UMK。新增证据要求包括真实 ES256 后端测试、虚拟 PRF 浏览器测试和部署时真实验证器联调。

通行密钥验收补充：新登记必须先验证同一凭证 get() 实际输出可用；创建与验证都有输出时必须一致。缺失/不一致不得留下服务端凭证包裹或成功提示，不可仅以 enabled 或创建阶段 PRF 判定解锁可用。实际提供方后续不可用时保持锁定，保留口令/RK 入口，错误不笼统归因于浏览器不支持。

通行密钥命名验收：型号读取不可用或超时必须回退系统名；默认名称包含浏览器与展示短编号，历史名称不强制迁移。名称和编号均非硬件身份或授权依据；重命名必须验证用户/租户/UMK 版本，保存修改审计，且不得写回公钥、签名计数、PRF 参数或 UMK 密文。

通行密钥诊断完成定义：仅在本标签页内存/控制台记录白名单元数据，100 条封顶、刷新清除，不自动上传；阶段编号能区分原生凭证调用、PRF 缺失/一致性、服务端校验和本地解包。禁止记录 PIN、口令、PRF/UMK、完整凭证及请求/响应/异常正文；以回归验证脱敏与异常分类，不把虚拟认证器通过当作真实提供方已修复。

附件校验完成定义补充：无固定魔数的文本格式不得仅因无 BOM 被判未知二进制。白名单内 `.md`/`.txt`/`.csv`/`.json`/`.xml`/`.css`/`.ts`/`.py`/`.java`/`.sql`/`.cs` 按严格 UTF-8 全文验证并保留原始内容，MIME 以扩展名为准；二进制签名/非法编码/控制字节必须拒绝。已有大小限制、鉴权、存储和扫描链路继续生效，不允许借文本格式绕过文件安全边界。

上传错误完成定义：客户端可修正的上传失败一律返回本地化业务错误 HTTP 400，不允许以 500 呈现。缺少扩展名、类型不在白名单或危险、格式无法识别、内容与扩展名/声明 MIME 不一致、超过大小上限必须使用各自错误码与中英文资源；错误响应不得回显内部路径、堆栈或原始异常文本，前端复用拦截器提示且不叠加通用失败消息。服务端存储故障仍按 500 处理并记录日志，不得伪装成客户端错误。
